# CianChatService — wiki

Шлюз между модулем «Чаты» ИК (SQL Server `re2a`) и чатами Циан (`public-api.cian.ru`). Клиент пишет по объявлению на Циан — сообщение попадает оператору ИК; оператор отвечает — ответ уходит клиенту в Циан.

---

## 1. Состав

| Исполняемый файл | Что это |
|---|---|
| `CianChatService.exe` | Боевая Windows-служба |
| `CianChatAssignmentService.exe` | Та же служба для переуступок (отдельный экземпляр со своим ini) |
| `CianChatFRTService.exe` | Та же служба для FRT (отдельный экземпляр со своим ini, порт 8116; ключ Циан будет выдан позже) |
| `CianChatExecute.exe`, `CianChatAssignmentExecute.exe`, `CianChatFRTExecute.exe` | Демо-приложения с окном: тот же функционал + кнопки ручных вызовов API |

- Код у всех шести общий, отличается только имя exe. Текущая версия всех exe — **1.1.0.0**.
- **Имя exe = имя службы = имя ini = имя лога.** Переименовали exe — переименуйте и ini, и службу.

## 2. Как работает

```
Циан ──POST вебхук──▶ tone.setl.ru (прокси) ──▶ служба :8114 /…cian…
                                                     │
                                                     ├─ разбор JSON, отбор новых входящих сообщений
                                                     ├─ БД: сессия → свободный оператор → чат/сообщение/файлы
                                                     └─ Циан API: автоответ клиенту

ИК (оператор) ──POST From=SETL&ChatId&Message + X-Setl-Token──▶ служба :8114 ──▶ Циан API send-message
```

**Входящее сообщение (вебхук)**
- Принимается POST, если в URI есть `cian` и сегмент пути `WebhookSecret` (если он задан). Без секрета — `404`. Не задан `Token` — `503`.
- Обработка идёт **до ответа**: `200` — всё сохранено; `400` — некорректный JSON; `500` — что-то не сохранено (ошибка БД, вложение не скачалось, чат не создан). На `500` Циан повторяет доставку, уже обработанные сообщения отсеиваются по `messageId`.
- Тело вебхука, получившего `500`, дополнительно сохраняется в `FailedWebhooks\` рядом с exe — на случай, если Циан не повторит доставку. Файлы содержат данные клиентов; разбирать вручную и удалять.
- Ошибка в одном чате не останавливает остальные; следующие сообщения этого чата ждут повторной доставки (сохраняется порядок).
- Неудачная отправка автоответа или ответа бота только пишется в лог и повтора не вызывает.
- Вебхуки обрабатываются строго по одному (защита от двойного чата).
- Пропускаются: исходящие (`direction` ≠ `in`), уже обработанные `messageId` (память процесса, сутки).
- На каждое сообщение:
  1. `VF_SetlTone_setUser` — сессия клиента.
  2. `VF_SetlTone_getFreeOperator_Cian` — оператор + текст автоответа.
  3. Оператора нет → офлайн-сообщение (`SetOfflineMessChatTel` / `UpdOfflineMessChatTel`) и ответ бота клиенту.
  4. Оператор есть → `VF_SetlTone_newChat_Cian`; новый чат → автоответ клиенту; вложения скачиваются в `PathTempFiles\<chat_id>\` и регистрируются `VF_SetlTone_setChatFile`.

**Исходящее сообщение (из ИК)**
- POST с параметрами `From=SETL` (именно параметр `From`), `ChatId` (число), `Message` (`\n` = перевод строки).
- Обязателен защитный токен: заголовок `X-Setl-Token` или параметр `SetlToken`.
- Сообщение отправляется в Циан до ответа (обычно около 1 с). Ответы: `200` Циан принял сообщение · `502` Циан вернул ошибку или недоступен (текст в теле) · `503` в ini службы не задан `Token` · `403` неверный токен · `400` неверный `ChatId` · `500` ошибка службы.
- Таймаут HTTP на стороне ИК — **не меньше 15 с**. Если ИК повторяет запрос по таймауту, а сообщение уже ушло, клиент получит его дважды.

**Секрет вебхука (`WebhookSecret`)**
- Циан не подписывает вебхуки, поэтому подлинность подтверждается секретным сегментом пути: `WebhooksURL=https://tone.setl.ru/chatcian2/<WebhookSecret>/`.
- Прокси `tone.setl.ru` должен передавать путь в службу без изменений (вместе с секретом).
- Секрет в лог не пишется (заменяется на `***`).
- Пустой `WebhookSecret` — проверка отключена, в логе предупреждение.
- Смена `WebhooksURL` оформляет новую подписку, старая остаётся у Циан. Порядок перехода: (1) со старым `WebhooksURL` и `SetUnSubscribe=1` запустить службу один раз — отписка; (2) прописать новый `WebhooksURL` и `WebhookSecret`, вернуть `SetUnSubscribe=0`, перезапустить — подписка на новый адрес; (3) проверить в логе `GetWebhooksSub`.

**Примеры вызова**

Два направления защищены РАЗНЫМИ секретами — не путать:

| Направление | URL | Что проверяется | `WebhookSecret` |
|---|---|---|---|
| ИК → служба (`From=SETL`, исходящие) | любой путь на `ServerPort` | `X-Setl-Token` | не нужен (URI в этой ветке не сверяется) |
| Циан → служба (вебхук, входящие) | путь содержит `cian` + сегмент секрета | `CheckWebhookSecret(URI)` | нужен, иначе `404` |

*Исходящее сообщение ИК → служба* (`From=SETL` — именно параметр; `ChatId`/`Message` url-encode'ить; перевод строки слать литералом `\n`):
```bash
curl -X POST "http://<сервер>:8114/" \
  -H "X-Setl-Token: <SetlToken из ini>" \
  -H "Content-Type: application/x-www-form-urlencoded; charset=utf-8" \
  --data "From=SETL&ChatId=123456789&Message=%D0%9F%D1%80%D0%B8%D0%B2%D0%B5%D1%82%0A%D1%81%D1%82%D1%80%D0%BE%D0%BA%D0%B02"
```
Тот же запрос токеном в теле (служба читает и заголовок, и параметр `SetlToken`):
```bash
curl -X POST "http://<сервер>:8114/" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data "From=SETL&ChatId=123456789&Message=текст&SetlToken=<SetlToken из ini>"
```
Ответы: `200` — принято Циан · `400` неверный `ChatId` · `403` пустой/неверный `SetlToken` · `502` Циан отверг/недоступен (текст в теле) · `503` в ini пустой `Token`. Синхронная отправка → таймаут ИК ≥ 15 с.

*Входящий вебхук Циан → служба* (POST на `WebhooksURL`, секрет обязателен сегментом пути; тело — JSON от Циан):
```bash
curl -X POST "https://tone.setl.ru/chatcian2/<WebhookSecret>/" \
  -H "Content-Type: application/json" \
  --data '{"operationId":"...","result":{"offersMessagesWebhook":{ ... }}}'
```
Без сегмента `WebhookSecret` (или с неверным) — `404`; прокси обязан передавать путь без изменений. Проверить приём можно тест-вебхуком Циан (`v1/send-test-webhook`) — это входящее направление, а не `From=SETL`.

**Старт службы**
- Читает ini, поднимает HTTP-сервер.
- В фоне проверяет подписку на вебхуки Циан и при необходимости подписывается (`offersMessagesIncoming` на `WebhooksURL`). Ошибка подписки не останавливает службу — смотреть лог.

## 4. Сборка

- Delphi **10.3 Rio**, Win32. Используются Indy, REST.Client, ADO (`SQLOLEDB.1`).
- Исходники `.pas` — в кодировке **cp1251**, не пересохранять в UTF-8 без BOM.
- Шесть проектов: `CianChatService`, `CianChatAssignmentService`, `CianChatFRTService`, `CianChatExecute`, `CianChatAssignmentExecute`, `CianChatFRTExecute`.
- Версия задаётся в `.dproj` (Project Options → Version Info) и при выпуске поднимается **во всех шести проектах одинаково**: `VerInfo_MajorVer/MinorVer/Release/Build` и строки `FileVersion`/`ProductVersion`.

## 5. Настройки (`<имя exe>.ini`, UTF-8, рядом с exe)

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `ServerPort` | 8114 | Порт HTTP-слушателя. **У двух служб на одном сервере — разные** |
| `LogHistPath` | LogHistory | Папка архива логов (относительно exe) |
| `MaxLogSize` | 1000000 | Размер лога до ротации, байт |
| `PathTempFiles` | `\\mserver\kk\Документы_по_чатам\` | Куда сохранять вложения |
| `ServerName` | mossqlcrp.corppn.ru | SQL Server (стенд: `mosqa01\instance1`) |
| `DBName` | re2a | БД (стенд: `re2a_stand`) |
| `DebugMode` | 0 | 1 — к сообщению в БД дописывается время |
| `CheckSubscribe` | 1 | Проверять подписку на вебхуки при старте |
| `SetSubscribe` | 1 | Подписаться, если подписки на `WebhooksURL` нет |
| `SetUnSubscribe` | 0 | Отписать `WebhooksURL` при старте (перекрывает `SetSubscribe`) |
| `WebhooksURL` | — | Публичный адрес, на который Циан шлёт вебхуки. Включает сегмент `WebhookSecret` |
| `WebhookSecret` | — | Секретный сегмент пути вебхука (≥ 32 символов, латиница и цифры). Пустой — проверка отключена |
| `MainDescription` | public-api.cian.ru | Код сайта для поиска оператора (`@FromSite`) |
| `Token` | — | **Ключ Циан API этой службы.** У каждой службы свой. Пустой — служба не работает с Циан |
| `SetlToken` | — | **Защитный токен для запросов ИК. Пустой — все запросы `From=SETL` отклоняются** |

- `Token` пустой или не задан — ключа по умолчанию нет: служба стартует, но не подписывается на вебхуки, а запросы `From=SETL` и вебхуки получают `503`. В логе `!!! Token is not set in ini`. Так работает FRT, пока не выдан ключ.
- Нет ini — служба стартует на значениях по умолчанию (боевая БД!) и пишет предупреждение в лог.

### ini в репозитории

| ini | `Token` | `SetlToken` | `WebhookSecret` |
|---|---|---|---|
| `ini/Debug/CianChatService.ini`, `CianChatExecute.ini` (стенд, порт 8114) | задан | задан (общий для пары) | пусто |
| `ini/Debug/CianChatFRTService.ini`, `CianChatFRTExecute.ini` (стенд, порт 8116) | пусто — ключ будет позже | пусто | пусто |
| `ini/Release/` | папка пустая | — | — |

- Боевые ini в репозитории не хранятся: они лежат на серверах рядом с exe. Перед заменой старой версии сверить их с разделом 7.
- FRT: `SetlToken` прописать **вместе** с `Token` (и сообщить ИК), иначе после выдачи ключа все запросы ИК получат `403`.
- `WebhookSecret` пустой везде — так задумано на время перехода (см. раздел 7).
- В Debug-ini ключ Циан и `SetlToken` записаны открытым текстом, а `ini` не исключён в `.gitignore`: при публикации репозитория они попадут в историю git.

## 6. Установка службы

Требования к серверу:
- Права администратора для регистрации.
- Служба работает под **LocalSystem** → к SQL Server подключается учётка компьютера `ДОМЕН\ИМЯПК$` (Integrated Security): ей нужны права на БД и процедуры.
- Учётке компьютера нужна запись в `PathTempFiles` (`\\mserver\kk\…`). Иначе файлы уйдут в temp профиля системы, и операторы их не откроют.
- Доступ к `https://public-api.cian.ru` без прокси (LocalSystem не видит прокси пользователя). Нужен прокси — настроить `netsh winhttp set proxy`.
- Входящий порт `ServerPort` открыт в брандмауэре для прокси `tone.setl.ru` и сервера ИК.

Регистрация (bat кладутся **рядом с exe**; имя службы определяется само, параметр-имя — только переопределение):

```
register_service_install.bat                :: имя службы берётся из *Service.exe рядом
register_service_install.bat CianChatAssignmentService   :: явное имя (переопределение)
register_service_create.bat                 :: тоже самое, через sc create
unregister_service_install.bat / unregister_service_create.bat
```

- **Автоопределение имени.** Если аргумент не задан, bat берёт имя из файла `*Service.exe` в своей папке (имя без расширения) — поэтому в папке каждой службы должен лежать **ровно один** `*Service.exe` (плюс свой ini, лог). Так `register_service_install.bat` без параметров регистрирует `CianChatService`, `CianChatAssignmentService` или `CianChatFRTService` — в зависимости от exe рядом. Если `*Service.exe` несколько, имя неоднозначно (цикл оставляет последнее по алфавиту) — уберите лишнее или передайте имя аргументом; если `*Service.exe` нет, откат на `CianChatService`.
- Иск именно `*Service.exe` (не `*.exe`) — чтобы случайно не зарегистрировать демо `*Execute.exe` как службу.
- Служба с exe, не оканчивающимся на `Service`, автоопределением не ловится — передайте имя аргументом.
- Оба способа ставят автозапуск и перезапуск при сбое (2 попытки через минуту); `sc description` = `CianChat.Setl.Corppn.ru`.
- При `sc create` вручную имя службы **обязано** совпадать с именем exe, иначе ошибка 1053.

### Регистрация и снятие всех трёх служб

Каждая служба — **своя папка** со своим exe + ini + логом и копиями bat. Bat обращается к
exe в своей папке (`%~dp0<имя>.exe`), запуск **от администратора**. Имя службы = имя exe,
поэтому в своей папке bat можно запускать **без аргумента** (имя возьмётся из `*Service.exe`).
`_install` регистрирует через `<exe> /install`, `_create` — через `sc create`; снимать тем же
способом, каким ставили.

Регистрация (по одной команде в папке каждой службы):
```
C:\WebService\CianChatService\>          register_service_install.bat
C:\WebService\CianChatAssignmentService\> register_service_install.bat
C:\WebService\CianChatFRTService\>       register_service_install.bat
```
Вместо `_install` — `_create`, если выбрана регистрация через `sc create`. Аргумент-имя
обязателен, только когда в папке лежит несколько `*Service.exe` (иначе имя неоднозначно)
или когда exe службы называется иначе, чем папка:
```
register_service_install.bat CianChatFRTService
```

Снятие с регистрации:
```
C:\WebService\CianChatService\>          unregister_service_install.bat
C:\WebService\CianChatAssignmentService\> unregister_service_install.bat
C:\WebService\CianChatFRTService\>       unregister_service_install.bat
```
(ставили через `sc create` — снимайте `unregister_service_create.bat`).

Проверка после регистрации:
```
sc query  CianChatService         :: служба существует
sc qc     CianChatService         :: имя службы = имя exe (иначе при старте 1053)
sc start  CianChatService
```
и в логе `<имя>_Log.txt`: нет `!!!`-предупреждений, `GetWebhooksSub` содержит текущий
`WebhooksURL`. Для FRT на старте ожидаемо `!!! Token is not set` (ключ ещё не выдан).

### Новая (ещё одна) служба

Отдельная служба = отдельная папка + exe с новым именем + свой ini. Пересборка не нужна.

1. Создать папку, например `C:\WebService\CianChatNewSite\`.
2. Скопировать туда `CianChatService.exe` под новым именем: `CianChatNewSite.exe`.
   - Имя — только латиница, цифры и `_` (без пробелов и `-`): оно же станет именем службы.
3. Положить рядом `CianChatNewSite.ini` и задать в нём **своё**:
   - `ServerPort` — свободный порт;
   - `Token` — ключ Циан этой службы;
   - `WebhooksURL` — свой адрес вебхуков (и маршрут на прокси до нового порта);
   - `WebhookSecret` — свой секрет (он же сегмент в `WebhooksURL`);
   - `SetlToken`, `ServerName`, `DBName`, `MainDescription`, `PathTempFiles`.
4. Скопировать в папку bat-файлы и выполнить: `register_service_install.bat CianChatNewSite`.
5. Проверить лог `CianChatNewSite_Log.txt`: нет `!!!`-предупреждений, подписка на вебхуки прошла.

## 7. Замена старой версии

Новая версия меняет поведение. Если заменить exe без подготовки, обмен с Циан остановится. Каждый пункт ниже — условие перехода без сбоев.

**Что проверить до замены**

| # | Что изменилось | Что будет, если не подготовить | Что сделать |
|---|---|---|---|
| 1 | Ключа Циан по умолчанию в коде больше нет | Служба с пустым `Token` не подписывается на вебхуки и отвечает `503`: входящие не приходят, ответы операторов не уходят | В боевом ini **каждой** службы задать `Token`. Если служба работала на ключе из кода, вписать его (старый `cToken` в `Classes.Inc.pas`, есть в истории git) |
| 2 | Запросы ИК требуют `SetlToken` | Все ответы операторов получают `403` | ИК начинает передавать `X-Setl-Token` в тот же момент; в ini службы тот же `SetlToken` |
| 3 | Имя службы = имя exe | Служба, зарегистрированная под другим именем (например, `CianChat`), не стартует — ошибка 1053 | `sc qc <имя>`; если имя ≠ имени exe — снять регистрацию и зарегистрировать заново bat-файлом |
| 4 | ini читается только как `<имя exe>.ini` рядом с exe | Старт на значениях по умолчанию: боевая БД, пустой `Token`, Циан отключён (`!!! Ini file not found`) | Положить ini рядом с exe под именем exe, в том числе для `CianChatAssignmentService` |
| 5 | Изменены процедуры `getFreeOperator_Cian`, `newChat_Cian`, `GetAutoAnswer_Cian` | Старый exe с новыми процедурами (или наоборот) работает с ошибками | Выкладывать строго по порядку (ниже) |
| 6 | Появился `WebhookSecret` | Секрет, включённый одновременно с заменой, отсекает все вебхуки, пока не настроены прокси и переподписка | При замене оставить `WebhookSecret` пустым и `WebhooksURL` прежним. Секрет включать отдельным шагом (раздел 2) |
| 7 | Ответ ИК — после отправки в Циан, бывают `502`/`503` | Короткий таймаут ИК с повтором приводит к дублям у клиента | Таймаут HTTP в ИК не меньше 15 с; проверить, как ИК обрабатывает ответы, отличные от `200` |
| 8 | Постоянные ошибки БД и файлов больше не гасятся, а вызывают повторную доставку | Одна и та же ошибка повторяется до 72 ч; в офлайн-ветке на каждом повторе создаётся новая офлайн-запись | Найти в логах старой службы повторяющиеся `*** Has error in TCianDBCore` и `GetMessageFile` и устранить причину до замены |

**Порядок замены**
1. Собрать все проекты и проверить на стенде: входящее сообщение, ответ оператора, вложение, ситуация без свободных операторов.
2. Подготовить боевые ini (пункты 1, 2, 4, 6) и ИК (пункты 2, 7).
3. Проверить регистрацию служб: `sc qc` (пункт 3).
4. Остановить старые службы.
5. Выполнить скрипты из `sql/`, подключившись к нужной БД. `VF_SetlTone_setUser.sql` **не выполнять** (раздел 8).
6. Заменить exe и запустить службы.
7. Проверить лог:
   - нет предупреждений `!!!`;
   - `GetWebhooksSub` содержит текущий `WebhooksURL`;
   - тестовое сообщение проходит в обе стороны.

**Что не нарушается при замене**
- Пока `WebhookSecret` пустой, адрес вебхука не меняется, и подписка у Циан сохраняется: переподписка не нужна.
- Короткий простой при замене не теряет входящие: Циан повторяет доставку, пока адрес недоступен (до 72 ч).
- Старая служба всегда отвечала `200`, поэтому у Циан не накопилось повторных доставок, которые новая служба обработала бы ещё раз.

## 9. Циан API

- Документация: https://public-api.cian.ru/docs/latest · спецификация OpenAPI: https://public-api.cian.ru/swagger/latest
- Авторизация `Authorization: Bearer <ключ>`; ключ выдаёт Циан (import@cian.ru), по одному на учётную запись.
- Используем: `v2/subscribe-webhooks`, `v2/unsubscribe-webhooks`, `v1/get-webhooks-subscriptions` (**устаревшие**, есть v3), `v1/send-message`, `v1/read-chat`, `v1/get-chat(s)`, `v1/get-messages`, `v1/get-message-file`, `v1/send-test-webhook`.
- Рекомендация Циан: не больше 10 запросов в секунду на метод.
- Вебхуки **не подписаны** (ни подписи, ни секрета) — подлинность подтверждается только секретным сегментом пути `WebhookSecret`.
- Повторная доставка при ошибке в документации прямо не описана; есть только правило 72 ч (ниже), из которого она следует. Поэтому тела необработанных вебхуков дополнительно сохраняются в `FailedWebhooks\`.
- Если URL вебхука недоступен больше 72 ч, Циан отключает подписку — после долгого простоя проверить лог старта.
- `get-messages` по умолчанию помечает чат прочитанным.

## 10. Логи и диагностика

- Лог: `<имя exe>_Log.txt` рядом с exe, архив — в `LogHistPath`.
- Префиксы: `-->` запрос, `<--` ответ, `+++ DB.` вызов БД, `***` ошибка, `!!!` предупреждение, `#` жизненный цикл.

| Симптом | Причина / что делать |
|---|---|
| Ошибка 1053 при запуске | Имя службы ≠ имя exe — перерегистрировать bat-файлом |
| Служба запущена, лога нет | Нет прав на запись в папку exe |
| `Has error in TCianChat.ServiceStart` + Socket Error | Порт занят (вторая служба/демо на том же порту) |
| `!!! Ini file not found` | ini не рядом с exe или назван не по имени exe |
| `!!! SetlToken is not set` | Задать `SetlToken` в ini |
| `!!! Token is not set in ini` / `Rejected: Token is not set` / `503` у ИК | Нет ключа Циан в ini — задать `Token` и перезапустить службу |
| `Send. Rejected: invalid SetlToken` | ИК шлёт неверный/пустой токен |
| `!!! Webhooks subscription check failed` | Нет доступа к Циан (прокси, сеть) или неверный токен — входящие не придут |
| `GetFreeOperator. Rejected: <xml>` | Клиент не найден или забанен |
| `SetNewChat. Chat is not created` | Нет свободного оператора / сессии; вебхук получит `500` и придёт повторно |
| `Chat is not processed, waiting for redelivery` | Сообщение не сохранено (причина — в той же строке и выше); ждать повторной доставки |
| `Webhook body saved: [...]` | Вебхук не обработан, тело в `FailedWebhooks\`; если повтор так и не прошёл — разобрать вручную |
| `Receiving. Rejected: invalid webhook secret` | Запрос без секрета: чужой запрос, старая подписка без секрета или прокси меняет путь |
| `!!! WebhooksURL does not contain WebhookSecret` | Секрет не добавлен в `WebhooksURL` — Циан будет слать на адрес без секрета, все вебхуки отклоняются |
| `Send. Response=[Error: ...]` / `Bad Gateway` у ИК | Циан отклонил сообщение (текст ошибки в ответе) или недоступен |
| Ошибки `EDatabaseError` | Права учётки компьютера на БД, доступность SQL Server |

## 11. Ограничения и открытые вопросы

- Постоянная ошибка (процедура возвращает не то, файл у Циан недоступен — ответ 4xx) приводит к повторам одного вебхука до 72 ч. Ответ 4xx на скачивание файла стоит не повторять, а пропускать с записью в лог — пока не сделано.
- `MainDescription` у FRT сейчас `public-api.cian.ru`, как у основной службы, поэтому операторы будут те же. Если для FRT нужны свои операторы, нужен отдельный сайт в `Attr867` и своё значение.
- `CianChatService` и `CianChatAssignmentService` (и пара Execute) имеют одинаковые `ProjectGuid` — мешает только при объединении в группу проектов (`.groupproj`).
- Две службы не должны работать с одним ключом Циан (`Token`) и разными `WebhooksURL`: каждое сообщение придёт в обе и будет обработано дважды.
- Защита от повторной доставки (`messageId`) живёт в памяти процесса и сбрасывается при рестарте; после рестарта дубль отсекает только `newChat_Cian` (сравнение с последним сообщением клиента).
- Совпадение `@FromSite = 'public-api.cian.ru'` с сайтом в `Attr867` (`https://public-api.cian.ru/`) зависит от `vf_getoperatorsite` — не проверено.
- В офлайн-режиме в БД пишется текст бота, а не сообщение клиента — уточнить по `UpdOfflineMessChatTel`.
- Отправка файлов оператором в Циан не реализована (API это умеет с 10.04.2026: `upload-file`, `send-message-with-files`).
- Нужен переход на v3 методов подписки.
